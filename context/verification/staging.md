# 스테이징 배포와 로그 확인

## 현재 상태
제안·미구축. 기존 실습 범위에는 운영 배포가 없다.
배포 대상과 비용·접근 권한을 결정하기 전에는 배포 명령을 실행하지 않는다.

## 목적
스테이징(실사용 환경에 올리기 전에 실행을 확인하는 별도 환경)에서 빌드 산출물을 검증한다.

## 사전 조건
도입할 경우 다음 항목을 먼저 확정한다.

| 결정 항목 | 필요한 내용 |
|---|---|
| 배포 대상 | 서비스, 주소, 비용, 담당자 |
| 접근 권한 | 배포 권한과 읽기 전용 로그 권한 |
| 워커 할당 | 실행 인스턴스별 고유 워커 ID, 교체 중 중복 방지 |
| 산출물 | CI에서 검증한 커밋과 JAR의 연결 |
| 준비 검사 | URL·인증 방식·시간 제한·기대 응답 |
| 복구 | 이전 버전, 중단 절차, 워커 재사용 위험 |

현재 구조는 재시작에 걸친 고유성을 보장하지 않는다.
롤백이나 롤링 배포에서도 같은 워커의 생성기가 겹치거나 시간·순번이 재사용될 수 있다.
이를 해결하지 않은 환경의 ID를 지속적인 고유성이 필요한 실제 데이터에 사용하지 않는다.

## 실행 방법
대상 확정 후 배포·버전 조회·준비 검사·HTTP 검사·로그 조회·중단 명령을 여기에 추가한다.
각 명령에는 실행 위치, 필요한 권한, 시간 제한, 기대 결과를 적는다.
AI의 읽기 검증과 배포·복구 실행 권한을 구분하고 허용된 범위에서만 수행한다.

## 성공 기준과 실패 시 확인
배포 커밋이 검증한 산출물과 같고 준비 검사와 HTTP 계약 검사가 성공해야 한다.
실패 시 배포 버전, 인스턴스, 워커 ID, 오류 코드와 시각을 함께 확인한다.
자격 증명과 전체 환경 변수는 로그로 남기지 않는다.
롤백했다고 ID 고유성 문제가 해결됐다고 판단하지 않는다.

## 정리 방법
실습 종료 시 배포 자원과 과금 여부를 확인한다.
로그 보관 기간, 자원 삭제 담당, 검증용 데이터 정리 범위를 도입 시 정한다.
