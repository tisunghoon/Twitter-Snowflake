# Snowflake 프로젝트 작업 안내

이 파일은 사용자가 작업을 맡길 때 지정하는 시작점입니다. 자동 로딩을 전제하지 않습니다.
현재 요청에 필요한 문서를 찾아 읽고 실행하는 순서를 안내합니다.

## 프로젝트 목적과 범위

Snowflake ID의 시간·워커 ID·순번 조합과 정렬·동시성·시계 역행을 학습하는 토이 프로젝트입니다.
구현 범위는 [설계](design.md), 확정 여부는 [결정 기록](decisions.md)을 기준으로 확인합니다.
현재 구현 상태와 다음 행동은 [진행 상태](progress.md)에 기록합니다. 이 파일에는 상태를 복사하지 않습니다.

## 시작 절차

1. 사용자의 요청이 설명, 문서 작성, 계획, 구현, 검증, 리뷰 중 무엇인지 확인합니다.
2. [설명과 문서 작성 지침](rules/explanation-and-documentation.md)을 읽고 답변과 문서에 적용합니다.
3. 기능 작업을 시작하거나 재개하면 [진행 상태](progress.md), [기능 목록](tasks.md),
   해당 기능의 plan.md와 관련 [결정](decisions.md)을 확인합니다.
4. 저장소 지침과 현재 변경 상태를 확인하고, 사용자의 기존 변경을 보존합니다.
5. 현재 작업·승인 상태·다음 행동을 짧게 알린 뒤 아래 표에서 필요한 문서와 코드를 읽습니다.

단순한 질문에는 관련 개념과 코드만 추가로 확인합니다. 전체 구현 절차를 시작하지 않습니다.
이미 승인된 범위는 다시 승인받지 않습니다. 읽지 못한 필수 문서는 확인했다고 표시하지 않습니다.

## 작업별 문서 안내

| 작업 | 읽을 문서 | 다음 행동 |
|---|---|---|
| 개념 설명 | [개념 노트](concepts.md), 관련 설계·코드 | 용어·이유·실제 동작을 설명합니다. |
| 설계·기능 작업 | [실습 스킬](skills/snowflake-practice/SKILL.md), [워크플로우](rules/workflow.md) | 요청한 단계부터 진행합니다. |
| 이슈 요청 작성 | [이슈 템플릿](templates/issue.md) | 목표·완료 조건·범위를 작성합니다. |
| 기능 계획 | [이슈 실행 규칙](rules/issue-execution.md), [기능 안내](features/README.md), [계획 템플릿](features/template.md), 관련 [설계](design.md)·[구조](architecture.md) | 기존 코드를 확인하고 변경·검증 계획을 제시합니다. |
| 구현 | 승인된 plan.md, 아래 코드 규칙 | 필요한 계층을 연결해 구현합니다. |
| 검증 | [검증 안내](verification/README.md), 관련 검사 문서 | 실제 명령을 실행하고 증거를 남깁니다. |
| 독립 리뷰 | [리뷰 템플릿](templates/review.md), 승인 계획·설계·실제 diff·코드·검증 증거 | 별도 컨텍스트에서 읽기 전용으로 검토합니다. |
| 완료 보고 | [완료 보고 템플릿](templates/completion-report.md) | 변경·검증·남은 위험·커밋을 보고합니다. |
| 훅 구축·문제 조사 | [훅 안내](hooks/README.md), 해당 훅 명세 | 지원 이벤트와 실제 동작을 확인합니다. |

구현 시에는 [디자인 패턴](rules/design-patterns.md), [클린 코드](rules/clean-code-principles.md),
[코드 컨벤션](rules/code-conventions.md), [협업 규칙](rules/collaboration-rules.md)을 적용합니다.
표의 문서를 한 번에 모두 읽지 않고 현재 단계와 변경 범위에 필요한 항목만 읽습니다.
문서 사이의 링크가 이 파일로 돌아오면 이미 읽은 진입 지침을 반복해서 읽지 않습니다.

## 실행 규칙과 완료 기준

메인 에이전트 하나가 기능의 계획·구현·자체 검증·리뷰 수정·커밋을 담당합니다.
기능 계획 승인 후 구현하며, 계약·범위를 바꾸어야 하면 변경 이유를 설명하고 확인받습니다.
이전의 Agy 구현·Codex 최종 검증 고정 분담은 사용하지 않습니다.

독립 리뷰는 메인 담당의 대화 이력을 상속하지 않는 새 컨텍스트에서 수행합니다.
Codex 협업 도구에서는 fork_turns="none"을 사용하고, 다른 호스트에서는 새 세션을 사용합니다.
기존 동료 패널이라는 이유만으로 독립 리뷰로 간주하지 않습니다.
리뷰어에게 리뷰 템플릿의 자료를 전달하고 세션 식별 정보를 기록합니다.

필수 검사 통과, 독립 리뷰 통과, 차단 결함 해소와 검증한 코드·최종 커밋의 일치가 완료 기준입니다.
실행하지 못한 필수 검사나 리뷰가 있으면 검증 보류로 보고합니다.
문서에 명령이 적혀 있다는 사실과 실제로 실행 가능한 상태를 구분합니다.
훅은 스크립트·호스트 연결·실행 검증이 확인돼야 활성 상태로 취급합니다.
push, 외부 메시지 전송, 이슈 변경·배포는 해당 요청과 권한이 있을 때만 수행합니다.

## 기록과 재개

- plan.md: 승인된 기능 범위, 완료 조건, 변경·검증 계획을 기록합니다.
- verification.md: 실행한 명령, 대상 버전, 결과와 미실행 항목을 기록합니다.
- review.md: 독립 리뷰, 발견 사항, 수정과 재검토 결과를 기록합니다.
- [tasks.md](tasks.md): 기능 목록과 상태를 연결합니다.
- [progress.md](progress.md): 현재 단계, 막힌 결정, 다음 첫 행동, 마지막 검증 근거를 갱신합니다.
- [decisions.md](decisions.md): 설계 선택의 제안·확정 여부와 이유를 기록합니다.

위의 기능별 세 파일은 context/features의 해당 기능 폴더에 둡니다.
세션 종료·단계 전환 때 최신 재개 지점을 갱신합니다. 상세 이력은 Git과 기능 기록에 남깁니다.
다음 세션은 실제 코드·변경 상태와 기록을 대조한 뒤 남은 작업부터 이어갑니다.

## 작업 요청 예시

```text
context/AGENT.md를 읽고 연결된 지침을 적용해 주세요.
작업 대상: [이슈 URL 또는 기능 요청]
기존 코드와 승인 상태를 확인하고 필요한 단계부터 진행해 주세요.
새 기능이면 계획을 먼저 제시하고, 승인된 작업이면 남은 단계부터 이어가 주세요.
```
