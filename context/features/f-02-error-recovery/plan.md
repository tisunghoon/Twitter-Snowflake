## 사용자 행동과 범위
사용자는 발급 불가 이유를 오류 코드로 구분하고, 유효한 시각으로 회복한 뒤 중복 없는 ID를 다시 받습니다.
F-01부터 존재해야 하는 방어를 재구현하는 작업이 아니라 실제 생성기→MVC 오류 응답→회복 성공의 연속 시나리오를 보강합니다.

## 변경 예상 (모두 예정)
- `src/test/java/com/example/snowflake/core/SnowflakeRecoveryTest.java`: 제어 Clock의 실패·회복과 성공 ID 집합을 검사합니다.
- `src/test/java/com/example/snowflake/api/IdRecoveryIntegrationTest.java`: 테스트 구성에서 Clock만 교체하고 실제 생성기·컨트롤러·예외 처리기를 사용합니다. 발급 결과 mock은 사용하지 않습니다.
- F-01의 `support/MutableClock.java`를 재사용합니다. 제품 core·API는 새 검사로 실제 결함이 드러난 경우만 수정합니다.

## 완료 조건과 구체적 검증
각 행은 독립 생성기로 시작합니다. epoch 기준 상대 시각을 사용합니다.

| AC | 시나리오 | 외부 결과 단언 |
|---|---|---|
| AC-01 | 고정 +10ms에 4096회 후 최소 2회 추가, +9→+10ms 복귀 | 성공 순번 0~4095·모든 ID 고유; 추가 2회와 복귀 모두 SEQUENCE_EXHAUSTED; +9ms는 CLOCK_ROLLBACK |
| AC-02 | 이 행 전용 새 생성기로 +10ms 4096회 발급·소진 오류를 직접 준비한 뒤, 같은 생성기를 +11ms로 변경 | 성공 sequence 0, 이 시나리오에서 발급한 직전 최대 ID보다 큼, 이어서 같은 ms seq1 |
| AC-03 | +10→+9→+10→+11ms | seq0→CLOCK_ROLLBACK→seq1→seq0; 성공 ID 고유·증가 |
| AC-04 | 최초 epoch-1 실패→epoch 성공; +10 성공→epoch-1/Long.MIN_VALUE/MAX_VALUE 실패→+10 복귀; 마지막 유효 ms와 다음 ms→마지막 ms 복귀 | 최초 회복 seq0; 범위 실패는 TIME_OUT_OF_RANGE; +10 복귀 seq1; 마지막 ms 성공 seq0→범위 실패→복귀 seq1 |
| AC-05 | 실제 생성기를 사용한 MVC 요청으로 위 소진·역행·범위 실패와 회복 | 각 오류 503·정확한 code·문자열 message, 성공 200·문자열 id와 복원 필드 일치; 실패 후 다음 성공 순번 유지 |

임의 RuntimeException의 웹 검사에서는 테스트 전용 실패 컴포넌트를 별도 컨텍스트에 넣어 도메인 code로 은폐되지 않는지 확인합니다. MVC가 미처리 예외를 전파하면 그 사실을 단언하며 임의로 503을 기대하지 않습니다.
핵심 회복 검증은 실제 생성기로 수행하고 내부 필드 반사 조회로 상태 보존을 대신하지 않습니다. 테스트 간 생성기 상태는 공유하지 않습니다.

## 실행 단계
1. 선행 core/API 검사를 실행하여 기준선을 기록하고 기존 AC와 중복 테스트를 식별합니다.
2. 위 회복 사례를 parameterized 또는 연속 동작 테스트로 작성합니다. F-01이 이미 만족하면 처음부터 GREEN인 사실을 기록하며 고의로 제품을 깨뜨려 RED를 만들지 않습니다.
3. 결함이 발견되면 해당 동작의 실패 단언을 먼저 기록하고 최소 수정 후 재실행합니다.
4. MVC의 실패→회복 시나리오 및 임의 예외 분리를 실행하고 전체 검사·실제 JAR HTTP 스모크를 회귀 검증합니다. 제어 시각 오류는 MVC에서, 실제 JAR은 정상 계약을 검사합니다.

- 커밋 2: `docs: 오류 회복 검증과 독립 리뷰 결과 기록` — 실제 증거와 재개 상태입니다.

## 공통 검증·리뷰·완료 절차
구현 직전 선행 기능 verification/review·커밋과 현재 검사 결과를 대조합니다. 새 버전·라이브러리는 추가하지 않고 F-01에서 실제 확인·고정한 도구를 재사용합니다.
전체 예정 명령: `JAVA_HOME=$(/usr/libexec/java_home -v 21) ./gradlew spotlessCheck check bootJar`와 `./scripts/verify.sh`입니다. 스크립트도 JVM 21을 지정합니다. Java 타입 검사는 main/test 컴파일로 확인합니다.
F-01의 공통 명령은 구축됐습니다. 기능별 예정 검사는 실제 실행 증거와 구분합니다. 로그·대상 코드·실행 환경·종료 코드·테스트 수·AC별 결과는 [verification.md](verification.md)에 기록합니다. UI가 없어 브라우저 검사는 적용하지 않습니다.
각 커밋은 논리 단위 300~400줄 이내이며 초과 시 테스트 시나리오/하네스 책임별로 나눕니다. 관련 변경만 스테이징하고 push·배포·무관한 리팩터링은 하지 않습니다.
자체 검사 후 `fork_turns="none"`의 새 컨텍스트 읽기 전용 리뷰어에게 승인 계약·설계·기준 커밋·새 파일 포함 diff·코드·실행 증거를 전달합니다. 발견 사항 수정 후 재검증하고 정확성 변경은 재리뷰합니다.
[review.md](review.md)에 리뷰 대상·세션·지적·수정·재검토를 기록합니다. 2패널 동료 계획 검수는 이 제품 독립 리뷰를 대신하지 않습니다.
관련 하위 단위도 검사·독립 검토 후 커밋하고 기능 전체 필수 검증·리뷰·차단 해소·커밋 일치 확인을 마친 뒤 다음 기능으로 이동합니다.
