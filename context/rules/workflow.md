# 워크플로우

이 문서는 설계 검토부터 구현과 최종 검증까지의 진행 순서를 정한다.
현재는 설계 초안 단계다. 규칙 문서를 만들었다고 구현 작업이 시작된 것은 아니다.

## 1. 현재 상태 확인

[agent.md](../agent.md)와 [실습 스킬](../skills/snowflake-practice/SKILL.md)을 읽는다.
이어서 design, decisions, tasks, progress 문서를 확인한다.
기존 변경과 확정 내용을 확인하고 이번 요청의 범위만 정한다.
구현·검증에서는 이 폴더의 디자인 패턴, 클린 코드, 컨벤션, 협업 규칙을 함께 참조한다.

## 2. 설계와 실행계획 확정

미정인 정책은 선택 이유와 대안을 제시하고 결정 기록에 상태를 남긴다.
구현 전에 논리 단위별 작업, 변경 범위, 예정 커밋 메시지를 제시하고 계획을 확인받는다.
이미 승인한 범위의 실행을 다시 승인받지는 않는다.
현재 D-02~07은 제안 상태이며 이를 요구하는 T-01~06은 기존 차단 상태를 유지한다.

## 3. 의존 순서대로 구현

| 순서 | 작업 | 주요 결과 |
|---|---|---|
| T-01 | 환경과 설정 | 실행 JVM·Wrapper 고정, 워커 설정 검사, Clock 구성 |
| T-02 | 생성과 복원 | 비트 규칙, 상태 전이, 경계 오류 |
| T-03 | HTTP API | 성공 DTO, 도메인 오류 응답 |
| T-04 | 동시성과 회귀 검증 | 고유성, 시간 경계, 다중 워커 검증 |
| T-05 | 실행 안내와 인계 | 재현 명령, 결과, 코드 버전, 제한 |
| T-06 | Codex 최종 리뷰 | 직접 검증, 결함 기록, 최종 판정 |

담당과 완료 조건은 [tasks.md](../tasks.md)를 따른다.
한 작업의 작성·검증을 마친 뒤 다음 작업으로 이동한다.
실제 테스트 명령은 빌드 도구가 확정되고 Wrapper가 생긴 뒤 기록한다.

## 4. 검증과 커밋

변경에 맞는 테스트를 실행한다. 문서만 바꾸면 링크·표현·설계 일치 여부를 확인한다.
기능 구현은 [설계의 검증 계약](../design.md)을 기준으로 확인한다.
성공 결과뿐 아니라 실패 후 상태 보존과 회복도 검사한다.

커밋은 한 논리 단위로 묶고 변경 줄 합산은 약 300~400줄 이내로 유지한다.
메시지는 `docs: 협업 규칙 정리`처럼 `태그: 한국어 설명`으로 쓴다.
태그는 `feat`, `fix`, `refactor`, `design`, `comment`, `chore`, `docs`, `hotfix`를 사용한다.
스테이징 대상은 이번 작업의 파일만 지정하고, 커밋 전에 diff를 확인한다.
push는 사용자가 직접 한다.

## 5. 독립 검토와 재개 기록

구현 Agy의 테스트 통과는 검증 대기 상태다.
Codex는 코드와 테스트의 단언을 읽고 관련 테스트를 직접 실행한다.
수정이 필요하면 구현 담당에게 연결하고 수정 후 관련 검증을 반복한다.
검토한 버전·실행 증거·미실행 항목·판정은 `context/review.md`에 남긴다.
실제 진행 상태와 다음 행동은 [progress.md](../progress.md)에 기록한다.

새 세션은 이 기록에서 이어간다. 완료한 설명과 작업을 처음부터 반복하지 않는다.
