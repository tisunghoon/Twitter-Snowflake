# Snowflake 기능별 개발

[역할](../../agent.md), [기능 규칙](../../features/README.md), [검증 안내](../../verification/README.md)를 읽는다.
사용자가 요청한 단계만 수행한다. 문서 작성 요청은 제품 구현 승인이 아니다.

## 학습과 설계
기존 concepts, design, decisions를 확인한다. 원문 사실·설계 제안·사용자 확정을 구분한다.
용어는 유지하고 첫 등장에 쉬운 뜻을 붙인다. 비유 → 작은 예 → 실제 동작을 연결한다.
원문을 못 읽었으면 그 범위를 밝히고 제목만으로 내용을 재구성하지 않는다.
비트·epoch·워커·역행·소진·재시작 정책은 확정 기록을 따른다.
작은 실습에 DB·UI·분산 조정을 임의로 추가하지 않는다.

## 기능 단위와 담당
작업 하나는 사용자 행동 하나를 끝까지 처리하는 단위다.
메인 에이전트 하나가 계획, 필요한 모든 계층의 구현, 자체 검증, 리뷰 수정, 커밋을 책임진다.
프론트·백엔드·DB별 구현 에이전트로 나누지 않는다. 해당 계층이 없으면 추가하지 않는다.
독립 리뷰는 새 컨텍스트의 별도 에이전트가 읽기 전용으로 수행한다.
이전의 Agy 구현·Codex 최종 검증 고정 분담은 이 규칙으로 대체한다.

## 1. 계획
기존 코드와 변경 상태를 읽고 [형식](references/task-format.md)에 따라 기능 계획을 작성한다.
사용자 행동, 성공·실패 조건, 변경 파일, API·DB·설정 영향, 테스트, 제외 범위를 적는다.
기준 커밋과 기존 미커밋 변경을 식별한다. 미정 값은 추측으로 확정하지 않는다.
기능 계획 승인 후 구현한다. 승인된 범위의 수정은 재승인을 요구하지 않는다.
계약·범위 변경이 필요하면 결정 기록과 계획을 갱신하고 확인받는다.

## 2. 구현
기능 전체를 순차 구현한다. 정확성에 필수인 검증과 동시성 보호를 후속 기능으로 미루지 않는다.
타인의 변경을 보존하고 파일별 수정 책임을 유지한다.
기반 작업은 기능을 실행하는 데 필요한 최소 범위로 제한한다.

## 3. 자체 검증
관련 테스트·컴파일 타입 검사·빌드·실행 검사를 실제 수행한다.
UI가 있으면 브라우저에서 정상·실패 상태도 확인한다. UI가 없으면 적용하지 않음을 적는다.
시간은 제어 가능한 Clock으로 검사하고 동시성 테스트의 모든 Future 결과를 회수한다.
실행 버전, 명령, 종료 코드, 테스트 건수, 로그, 미실행 항목을 기능 verification.md에 기록한다.
필수 환경이 없으면 검증 보류다. 통과한 것으로 간주하거나 완료를 선언하지 않는다.

## 4. 독립 리뷰
새 컨텍스트 리뷰 에이전트를 시작한다. 전체 구현 대화나 성공 주장을 판단 근거로 넘기지 않는다.
승인 요구사항, 관련 설계·규칙, 기준 커밋과 현재 diff, 코드·테스트, 실행 증거를 전달한다.
리뷰어는 요구사항 누락·경계·동시성·회귀·잘못된 테스트 단언을 직접 확인한다.
발견 사항은 심각도·파일/줄·근거·기대 동작·차단 여부로 review.md에 기록한다.
새 컨텍스트를 제공할 수 없으면 독립 리뷰 대기로 두고 자기 리뷰로 대체하지 않는다.

## 5. 수정·재검증·커밋
메인 에이전트가 수정하고 관련 검사를 다시 실행한다.
정확성에 영향을 주는 수정은 리뷰어가 변경된 diff를 재검토한다.
필수 검증 통과, 독립 리뷰 통과, 차단 결함 해소 후 기능 변경만 작은 커밋으로 남긴다.
리뷰 후 코드가 바뀌면 해당 검증·리뷰를 갱신한다. 검증한 코드와 커밋한 코드가 같아야 한다.
커밋은 논리 단위당 약 300~400줄 이내로 나누고 push는 하지 않는다.
큰 기능은 검토 가능한 하위 커밋으로 나눌 수 있지만 기능 전체 완료 조건은 유지한다.
기능 기록과 tasks·progress를 갱신한 뒤 다음 기능의 계획으로 이동한다.
