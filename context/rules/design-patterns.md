# 디자인 패턴

이 문서는 [설계 초안](../design.md)과 [예상 아키텍처](../architecture.md)의 구조를 설명한다.
구현 코드는 아직 없다. 아래 적용 예정 구조는 제안이며, 확정 여부는 [결정 기록](../decisions.md)을 따른다.
문서 생성은 D-02~07의 승인이나 구현 착수 지시를 뜻하지 않는다.

## 책임별 계층 분리

계층 분리(역할에 따라 코드를 나누는 구조)를 적용할 예정이다.

| 패키지 | 책임 | 넣지 않을 내용 |
|---|---|---|
| `api` | 요청 수신, 응답 DTO 작성, 도메인 오류를 HTTP로 변환 | 비트 계산, 순번 갱신 |
| `core` | ID 생성, 필드 복원, 생성 규칙과 오류 | Spring 애너테이션, HTTP 상태 코드 |
| `config` | 설정 검사, Clock과 생성기 Bean 연결 | 요청별 ID 생성 과정 |

`api`는 `core`를 호출한다. `core`는 `api`와 `config`에 의존하지 않는다.
현재 범위에는 저장 기능이 없으므로 Repository를 추가하지 않는다.
호출을 전달하기만 하는 Service 계층도 의무적으로 만들지 않는다.

## 의존성 주입과 시간 교체

의존성 주입(DI: 객체가 필요한 재료를 외부에서 받는 방식)을 사용한다.
`SnowflakeGenerator`는 생성자로 `workerId`와 `Clock`을 받는다.
운영에서는 실제 시계, 테스트에서는 시간을 지정할 수 있는 시계를 넣는다.
생성기 안에서 시스템 시간을 직접 읽으면 테스트에서 시계 역행을 재현하기 어렵다.

이는 시간 공급 방식을 교체한다는 점에서 전략 패턴(같은 역할의 동작을 바꿔 끼우는 방식)과 닮았다.
별도의 시간 인터페이스를 추가하지 않고 기존 `Clock` 추상화를 사용한다.
오류 정책을 교체하는 전략 클래스들은 현재 설계에 포함하지 않는다.

## 생성기 수명과 공유 상태

생성기는 애플리케이션 컨텍스트에서 Bean 하나로 구성하는 안이다.
요청마다 새 생성기를 만들면 이전 순번을 잃어 같은 ID를 발급할 수 있다.
정적 `getInstance()`를 가진 직접 구현 Singleton 패턴은 사용하지 않는다.
Bean 하나라는 조건은 여러 서버 전체에 생성기가 하나라는 뜻이 아니다.
프로세스마다 서로 다른 워커 ID를 배정해야 한다.

## DTO와 오류 변환

DTO(계층 사이에 값을 전달하는 객체)는 `IdResponse`, `ErrorResponse`에 사용한다.
`IdParts`는 복원 결과를 담는다. 생성기의 변경 가능한 상태는 응답으로 노출하지 않는다.
도메인 예외는 API 예외 처리기가 HTTP 응답으로 바꾼다.
모든 예외를 생성 실패로 처리하지 않고, 설계에서 정한 오류만 변환한다.

새 패턴은 해결할 문제와 기존 구조로 해결하기 어려운 이유를 먼저 기록한 뒤 도입한다.
