# 테스트용 DB와 데이터

## 현재 상태
테스트 데이터 준비 예정. DB는 현재 범위에 없으므로 적용하지 않는다.
DB 연결 설정, 컨테이너, 초기 SQL은 만들지 않는다.

## 목적과 사전 조건
시간과 워커 값을 직접 지정해 같은 실패를 반복해서 재현한다.
아래 숫자는 현재 비트 배분·epoch 제안에 해당하며 변경 시 함께 수정한다.

## 데이터 준비 방법
| 재료 | 준비할 값 |
|---|---|
| epoch | 2026-01-01T00:00:00Z |
| 시간 경계 | epoch-1ms, epoch, epoch+(2^41-1)ms, 그 다음 ms |
| 역행·회복 | epoch+10ms → +9ms → +10ms → +11ms |
| 워커 | 0, 1, 2, 1023, 잘못된 값 -1과 1024 |
| 순번 소진 | 한 시각에서 4096회 성공 후 1회 추가 호출 |
| 알려진 결과 | epoch+1ms, worker 1, sequence 0이면 ID 4198400 |

테스트용 Clock은 시간을 명시적으로 변경할 수 있고 동시 접근에서도 일관된 값을 제공해야 한다.
테스트마다 Clock과 생성기를 새로 만들고 static 상태를 공유하지 않는다.
동시성 검사 동안은 시간을 고정해 결과를 예측할 수 있게 한다.
운영 코드에 시간 변경용 HTTP API를 추가하지 않는다.

## 성공 기준
테스트 순서를 바꾸거나 개별 테스트만 실행해도 같은 결과가 나온다.
고정 기대값은 생성기·Decoder를 호출해서 다시 만들지 않는다.
임의 데이터를 추가하면 seed(난수 재현에 쓰는 초기값)를 실패 결과에 남긴다.

## 실패 시 확인
시간 단위, epoch, 이전 테스트 상태 누출, 워커 중복 여부를 확인한다.
서로 다른 프로세스에 같은 워커 ID를 주면 고유성 전제가 깨진다.

## 정리 방법
각 테스트가 만든 객체와 스레드만 정리한다.
추후 DB 기능이 생기면 격리된 테스트 DB, 초기 데이터, 초기화·삭제 범위를 별도로 설계한다.
