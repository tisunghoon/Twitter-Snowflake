# F-04: 두 워커 서버에서 ID 발급

## 상태와 승인
- 원문 요청: 현재 대화의 F-01~04 문서 작성 및 Agy 작업 지시입니다. GitHub 이슈는 생성하지 않았습니다.
- 상태: 계획 초안 작성. 선행 기능과 상세 계획 확인 후 순차 진행합니다.
- 메인 담당: Herdr 구현 담당 Agy(wG:p3). 실제 전달 시 세션을 확인합니다.
- 선행 기능: F-03의 검증·독립 리뷰·커밋 완료입니다.
- 기준 커밋 / 기존 변경: 구현 시작 시 선행 결과와 작업 트리를 기록합니다.
- 승인 범위: 작업 착수·담당 인계 요청을 받았습니다. D-02~07의 미정 사항은 기존 승인 기록과 대조합니다.

## 사용자 행동
사용자는 서로 다른 워커 ID와 포트로 두 서버를 실행하고 각 서버에서 ID를 발급받습니다.

## 기존 코드 확인
[AGENT.md](../../AGENT.md), [설계](../../design.md), [결정](../../decisions.md)을 읽습니다.
현재 제품 코드는 없습니다. 구현 시 선행 기능의 코드와 검증 결과를 읽고 재사용할 부분을 적습니다.

## 범위와 계약
D-05의 수동 워커 할당 제안을 기준으로 작성했습니다.
worker 1·2의 프로세스 두 개를 실행합니다. 각 서버는 자기 상태를 유지합니다.
자동 워커 할당·중복 설정 자동 탐지·재시작 이후 고유성·운영 배포·DB·UI는 제외합니다.

## 변경 예상
- README: JDK·실행 JAR·워커·포트 설정을 포함한 복사 가능한 명령을 작성합니다.
- 검증 스크립트: 두 서버 시작·준비·요청·결과 합산·종료를 구현합니다.
- core 다중 워커 테스트: 동일 시각을 강제해 고유성을 검사합니다.
- config 테스트: 워커 누락·범위 오류와 기본값 부재를 확인합니다.
- 예정 스크립트 이름은 scripts/multi-worker-smoke-test.sh이며 선행 구조에 맞춰 확정합니다.

## 완료 조건과 검증
아래 수치·오류 정책은 현재 설계 제안 기준이며 확정 결정이 바뀌면 함께 갱신합니다.

| 조건 | 입력·동작 | 기대 결과 |
|---|---|---|
| AC-01 | 서로 다른 포트와 worker 1·2로 시작 | 두 서버 준비 성공, 응답에서 각 worker 복원 |
| AC-02 | 같은 고정 시각에서 worker 1·2 각각 2048회 | 총 4096개 성공 ID가 모두 고유 |
| AC-03 | 실제 두 서버에 각각 2048회 발급 | 총 4096개 성공 ID가 모두 고유, 각 워커·복원 필드 일치 |
| AC-04 | 워커 미설정·-1·1024 | 시작 실패, 임의 기본 워커로 실행되지 않음 |
| AC-05 | 요청 실패·시작 실패·포트 충돌·중단 | 자신이 띄운 서버만 정리하고 원인·로그 보존 |
| AC-06 | 실행 안내 확인 | 같은 워커 재사용·재시작 중복 가능성, 전역 엄격 정렬 미보장을 명시 |

실제 서버 시계가 정확히 같다고 가정하지 않습니다. 같은 ms 조건은 AC-02에서 별도로 증명합니다.
실제 서버 요청은 워커당 순번 용량 이내로 제한하고 모든 응답을 회수합니다.
검증 스크립트는 기존 프로세스를 종료하지 않고 자신이 만든 PID만 정리합니다.
핵심 동작 테스트의 실패를 먼저 확인한 뒤 구현하고 재검증합니다.
선행 검증 결과와 현재 관련 검사 결과를 회귀 기준선으로 기록합니다.
[검증 안내](../../verification/README.md)에 따라 관련 테스트·Java 컴파일·빌드·HTTP 검사를 실행합니다.
현재 명령은 미구축입니다. 선행 기능의 실제 명령을 확인해 plan.md에 기록합니다.
UI가 없으므로 브라우저 검사는 적용하지 않습니다. 미실행 필수 검사는 검증 보류로 보고합니다.

## 결정과 커밋
구현 전에 기존 승인 범위와 계약을 확인하고 미정 사항·변경 필요 사항만 사용자에게 제시합니다.
예정 커밋은 기능 수정과 관련 검증·실행 안내를 논리 단위로 나눕니다. 무관한 리팩터링은 제외합니다.

실행 증거는 [verification.md](verification.md), 독립 리뷰는 [review.md](review.md)에 남깁니다.
