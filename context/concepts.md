# Snowflake를 직접 만들기 전에

## 원문에서 가져오는 출발점

[Twitter의 2010년 발표](https://blog.x.com/en/engineering/announcing-snowflake)는
여러 곳에서 생성하는 대략 시간순인 64비트 ID를 위해 시간·워커 번호·시퀀스를 조합한다.
구체적인 비트 수와 예외 정책은 이번 실습에서 선택한다.
아래 비유·계산·구현 정책은 이해를 위한 설명과 실습 설계다.

## 1. 이름표가 겹치면 왜 곤란할까?

장난감 두 개에 모두 7번을 붙이면 “7번 가져와”라는 말을 알아듣기 어렵다.
서버 두 대가 각각 1, 2, 3번을 발급해도 같은 문제가 생긴다.
ID는 물건을 구별하는 이름표다. 이름표를 발급할 때마다 중앙 창구에 묻지 않으려면
각 발급기의 번호가 겹치지 않게 정해져 있어야 한다.

## 2. 세 가지 정보를 한 숫자에 넣기

이름표에 “언제 만들었는지 / 어느 로봇인지 / 그때 몇 번째인지”를 적는다.

| 비유 | 실제 용어 | 역할 |
|---|---|---|
| 시계 | timestamp | 서로 다른 ms를 구별 |
| 로봇 번호 | worker ID | 같은 ms에 일하는 다른 생성기를 구별 |
| 그 순간의 순번 | sequence | 같은 생성기가 같은 ms에 여러 개 만들 때 구별 |

1ms는 1초를 1,000조각 낸 시간이다. 시계만 쓰면 같은 조각 안의 요청이 겹친다.
로봇 번호만 쓰면 같은 로봇의 다음 요청이 겹친다. 세 필드를 함께 사용해야 한다.
단, 로봇 번호를 중복 배정하거나 이전 시간·순번을 재사용하면 여전히 중복될 수 있다.

## 3. 비트는 작은 칸, 시프트는 자리 만들기

비트 한 칸에는 0 또는 1만 들어간다. 2칸에는 00, 01, 10, 11의 네 가지가 들어간다.
학습용으로 시간 4칸·워커 2칸·순번 2칸을 잡아 보자. 실제 설계보다 작은 예시다.

```text
시간 3        워커 1    순번 2
0011          01        10
합친 값: 0011 01 10 = 54
(3 << 4) | (1 << 2) | 2 = 48 + 4 + 2 = 54
```

`<<`는 오른쪽에 빈 칸을 만들고, `|`는 겹치지 않는 필드들을 합친다.
`54 >>> 4`는 시간 3을 꺼낸다. `(54 >>> 2) & 3`은 워커 1,
`54 & 3`은 순번 2다. `& 3`은 끝의 두 칸(이진수 11)만 남기는 마스크다.
비유의 종이 이름표와 달리 실제로는 문자열을 이어 붙이지 않고 정수의 자리를 조작한다.

## 4. 시간을 어디서부터 셀까? — epoch

운동장에서 선생님이 “지금부터 시작!” 하고 초시계를 눌렀다고 생각해 보자.

- 시작한 순간에는 초시계가 **0**이다.
- 1초 뒤에는 **1**이다.
- 2초 뒤에는 **2**다.

여기서 **“시작!”이라고 정한 순간**을 어려운 말로 **epoch(에포크)**라고 한다.
시간을 세기 위한 출발점이라는 뜻이다.

우리 번호표에도 “출발점부터 얼마나 지났는지”를 적는다.
예를 들어 출발점을 오늘 아침 9시로 정했다면 다음과 같다.

| 현재 시각 | 출발점부터 지난 시간 |
|---|---|
| 오전 9시 정각 | 0초 |
| 오전 9시 1초 | 1초 |
| 오전 9시 2초 | 2초 |

실제 프로그램에서는 초보다 작은 **밀리초(ms)**로 센다. 1초는 1,000ms다.
출발점에서 1초가 지났다면 시간 칸에 1,000을 넣는다.

**왜 출발점이 필요할까?** 번호표에는 시간을 넣을 자리가 한정되어 있다.
우리가 정한 날부터 지난 시간만 세면 그 자리를 앞으로 쓸 수 있다.
다만 초시계처럼 실제 컴퓨터 시계를 0으로 바꾸지는 않는다.
프로그램이 **현재 시각에서 출발 시각을 빼서** 지난 시간을 구한다.

모든 로봇은 같은 출발점을 써야 한다. 빨강 로봇의 “1초 지남”과
파랑 로봇의 “1초 지남”이 같은 시각을 뜻해야 번호를 비교할 수 있기 때문이다.

이번 설계에서는 **2026년 1월 1일 00:00:00 UTC**를 출발점으로 제안했다.
UTC는 모두가 함께 쓰기로 정한 세계 시간 기준이다. 한국 시간으로는 그날 오전 9시다.
이 날짜는 특별한 정답이 아니라, 이번 프로젝트에서 함께 정할 약속이다.

> 여기서는 “epoch = 시간을 세기 시작하는 출발점”만 기억하면 된다.

## 5. 같은 순간에 번호표를 너무 많이 달라고 하면? — 순번 소진

이제부터 번호표를 **[시간 / 로봇 / 순번]**으로 펼쳐서 보자.
실제 ID는 한 숫자지만, 설명에서는 세 부분을 나눠 적겠다.

빨강 로봇이 한 순간에 쓸 수 있는 순번이 **0, 1, 2, 3**뿐이라고 가정하자.
이는 이해를 위한 작은 예시다. 설계 제안에서는 0~4095를 쓴다.

아직 시계가 10ms를 가리키는 동안 네 명에게 번호표를 줬다.

| 요청 | 나눠준 번호표 |
|---|---|
| 첫 번째 | [10 / 빨강 / 0] |
| 두 번째 | [10 / 빨강 / 1] |
| 세 번째 | [10 / 빨강 / 2] |
| 네 번째 | [10 / 빨강 / 3] |

그런데 시계가 여전히 10ms인데 다섯 번째 요청이 왔다.
**쓸 수 있는 순번을 모두 사용했다.** 이것을 순번 소진이라고 한다.

여기서 순번을 다시 0으로 만들면 **[10 / 빨강 / 0]**이 된다.
첫 번째 사람에게 준 번호표와 똑같으니 그렇게 하면 안 된다.

대신 시계가 11ms가 되면 **[11 / 빨강 / 0]**을 줄 수 있다.
순번은 다시 0이지만 **시간 칸이 달라졌으므로 다른 번호표**다.

다섯 번째 요청을 처리하는 방법은 두 가지다.

- **기다리기:** “시계가 11ms가 될 때까지 기다려 주세요.”
- **실패 알리기:** “지금은 번호표를 만들 수 없어요.”라고 바로 응답한다.

이번에는 두 번째 방법을 제안했다. 시계가 멈춰도 요청이 끝없이 기다리지 않아서
실습 중 무슨 일이 생겼는지 확인하기 쉽다. 실패한 요청에 번호표를 주는 것은 아니다.
나중에 새로운 요청이 왔을 때 시간이 다음 ms로 바뀌었다면 발급할 수 있다.

> 순번을 다 썼다면 같은 시간 안에서 처음 순번을 다시 쓰면 안 된다.

## 6. 시계가 뒤로 가면? — 시계 역행

컴퓨터의 시계도 시간을 맞추는 과정에서 뒤로 조정될 수 있다.
방금 10ms였는데 다음에 확인하니 9ms인 상황이다. 이것을 **시계 역행**이라고 한다.

빨강 로봇이 다음 번호표를 이미 줬다고 하자.

```text
조금 전: [9 / 빨강 / 0]
방금:    [10 / 빨강 / 0]
```

그런데 시계가 다시 9ms가 됐다. 로봇이 “다른 시간이네, 순번을 0부터 시작하자”라고
처리하면 **[9 / 빨강 / 0]**을 또 만들게 된다. 이미 준 번호표와 겹친다.

그래서 로봇에게 작은 메모를 남기게 한다.

```text
마지막으로 발급한 시간: 10ms
그때 사용한 순번: 0
```

다음 요청에서는 시계와 메모를 비교한다. 이번 제안은 다음과 같다.

| 지금 시계 | 로봇의 행동 | 이유 |
|---|---|---|
| 9ms | 발급하지 않고 오류를 알림 | 마지막 발급 시간보다 뒤로 갔음 |
| 다시 10ms | [10 / 빨강 / 1] 발급 | 같은 시간이므로 이전 순번 다음을 사용 |
| 11ms | [11 / 빨강 / 0] 발급 | 시간이 더 커져서 순번을 처음부터 사용 가능 |

오류가 났다고 메모를 지우면 안 된다. 메모가 있어야 이미 준 번호를 피할 수 있다.
같은 10ms로 돌아왔는데 순번까지 모두 쓴 상태라면, 5번에서 설명한 소진 오류를 알린다.

> 시계가 마지막 발급 시간보다 뒤로 갔다면, 이번 설계에서는 번호를 주지 않는다.

## 7. 두 요청이 동시에 오면? — 동시성

한 로봇이 두 손으로 번호표를 나눠준다고 생각해 보자.
메모에는 “마지막 순번은 6”이라고 적혀 있다.

```text
왼손: 메모를 읽는다 → 다음은 7이네!
오른손: 메모를 읽는다 → 다음은 7이네!
왼손: 7번을 준다.
오른손: 7번을 준다.  ← 중복!
```

**두 요청이 같은 메모를 읽고, 둘 다 다음 번호를 골랐기 때문**이다.
이처럼 여러 일이 겹쳐 진행될 때를 다루는 것이 동시성 문제다.

해결하려면 메모를 사용하는 동안 다른 손이 기다리게 하면 된다.

```text
왼손: 메모 읽기 → 7 선택 → 메모를 7로 고치기 → 끝
오른손: 그다음 메모 읽기 → 8 선택 → 메모를 8로 고치기 → 끝
```

이번 Java 설계에서는 이 구간을 `synchronized`로 보호하자고 제안했다.
지금은 **“번호를 고르고 메모를 고치는 작업은 한 번에 한 요청만 한다”**고 이해하면 된다.
시간을 확인하는 작업도 이 구간에 포함한다.

이 규칙은 **같은 생성기 안에서** 적용된다. 다른 서버의 로봇까지 줄 세우지는 않는다.
서로 다른 로봇은 서로 다른 워커 번호를 써서 번호표를 구별한다.

## 8. 숫자가 작은 번호표가 항상 먼저 만들어졌을까? — 정렬

한 로봇이 정상적으로 발급하면 다음처럼 진행된다.

```text
[10 / 빨강 / 0] → [10 / 빨강 / 1] → [11 / 빨강 / 0]
```

시간을 숫자의 앞쪽 자리에 넣었으므로, 시간이 커지면 전체 ID도 커진다.
같은 시간·같은 로봇에서는 순번이 커지므로 전체 ID가 커진다.

하지만 **서로 다른 로봇의 시계가 다를 수 있다.**

| 실제로 일어난 순서 | 로봇이 보고 있는 시간 | 번호표 |
|---|---|---|
| 먼저 파랑 로봇이 발급 | 빠르게 가는 시계: 12ms | [12 / 파랑 / 0] |
| 나중에 빨강 로봇이 발급 | 느리게 가는 시계: 10ms | [10 / 빨강 / 0] |

나중에 만든 빨강 번호표가 숫자로는 더 작다.
그래서 여러 서버에서 만든 ID를 숫자순으로 정렬해도 **실제로 만든 순서와 항상 같지는 않다.**
서버들의 시계가 비슷하게 맞아 있을 때 대략적인 시간 순서를 나타낸다고 이해하자.

또, 먼저 만든 번호표라도 인터넷 전달이 늦으면 나중에 도착할 수 있다.
**번호를 만든 순서와 응답을 받은 순서도 다를 수 있다.**

> “번호가 서로 다르다”와 “실제 시간 순서를 정확히 알려 준다”는 별개의 약속이다.

## 9. 프로그램을 껐다 켜면 메모는 어떻게 될까?

이번 로봇의 메모는 프로그램이 실행되는 동안의 기억에만 있다.
프로그램을 끄면 “마지막 시간과 순번”을 잊는다.

같은 로봇 번호로 다시 시작했는데 시계가 전에 사용한 시간으로 돌아가 있거나,
아직 마지막 발급 ms가 지나지 않았다면 옛 번호표를 다시 만들 수 있다.

이를 막으려면 메모를 꺼져도 남는 곳에 저장하는 등 추가 설계가 필요하다.
이번 작은 실습에서는 그 기능까지 만들지 않기로 **제안**했다.
따라서 “껐다 켜도 절대로 중복되지 않는다”고 약속하지 않는다.

> 이번 실습은 로봇이 기억을 유지하며 실행 중인 상황부터 제대로 다룬다.

## 작은 예제로 다시 확인하기

계산보다 이야기를 따라가 보자. 막히는 항목만 질문해도 된다.

1. “오전 9시부터 시간을 센다”에서 epoch는 언제일까? → 오전 9시.
2. [10 / 빨강 / 0]과 [11 / 빨강 / 0]은 같을까? → 시간 칸이 달라서 다르다.
3. 마지막으로 10ms에 발급했는데 시계가 9ms가 됐다면? → 발급하지 않고 오류를 알린다.
4. 두 손이 동시에 같은 다음 순번을 고르지 않으려면? → 메모를 한 손씩 사용한다.
5. 먼저 도착한 응답이 반드시 먼저 만들어진 ID일까? → 전달이 지연될 수 있어 그렇지 않다.

이 이야기가 이해되면 코드에서는 **시계 읽기 → 메모 비교 → 순번 선택 → 메모 갱신**이
어디에 있는지 찾아보면 된다. 아직 설계 제안의 승인을 뜻하지는 않는다.
