## 완료 조건과 구체적 검증

| AC | 입력·실행 | 단언 |
|---|---|---|
| AC-01 | 새 생성기, 고정 ms, 8스레드×256회 | 성공 2048, 고유 ID 2048, 복원 sequence 집합 정확히 0~2047, 시간·워커 일치 |
| AC-02 | 별도 새 생성기, 고정 ms, 8스레드가 총 4097회 분담 | 성공 정확히 4096·SEQUENCE_EXHAUSTED 정확히 1, 성공 순번 집합 0~4095; 같은 ms 후속 호출도 소진 유지 |
| AC-03 | 실제 서버, 시스템 Clock, 8개 작업자가 각 256개 POST 수행 | 성공 2048·고유 ID 2048, 모든 응답 문자열 id·복원 시각·워커·순번 일치; 모든 응답 회수 |
| AC-04 | 작업 예외·HTTP 실패·timeout을 각각 테스트 하네스에 주입 | 실패가 전체 검사 실패로 드러나며 무한 대기 없음; executor 종료·서버 컨텍스트 종료 확인 |
| AC-05 | 별도 순차 요청과 동시 요청 결과 | 순차 성공 ID만 엄격 증가; 동시 결과는 집합으로 검사하며 응답 도착 순서를 단언하지 않음 |

시작 장벽의 참여자는 8개 작업자와 메인입니다. 2048개 task를 모두 대기시키는 구조를 만들지 않습니다.
작업 예외는 Future.get에서 드러내고, 도메인 소진만 명시적으로 집계합니다. 예상 밖 예외를 소진으로 세지 않습니다.
실패 발견 후에도 모든 Future를 회수하거나 취소하여 누락을 명시하고 finally에서 shutdownNow/awaitTermination을 수행합니다.
장벽 대기 10초, HTTP 요청당 5초, 전체 작업 60초의 단일 deadline을 사용합니다. Future마다 전체 timeout을 새로 주어 누적 대기를 허용하지 않습니다.
HTTP 준비는 30초 한도 내 실제 POST의 200·JSON 확인으로 판단하고, 성공 확인 1회 뒤 멈춥니다. 준비 중 성공 응답도 별도 기록합니다. 본 요청 2048개와 준비 발급 수 합계가 4096 미만인지 검사합니다.
실시간 시계 역행이나 소진으로 503이 나오면 재시도로 숨기지 않고 코드·시각을 기록해 검증 실패/보류로 구분합니다. 고정 ms 증명은 AC-01/02에서 수행합니다.

## 공통 검증·리뷰·완료 절차
구현 직전 선행 기능 verification/review·커밋과 현재 검사 결과를 대조합니다. 새 버전·라이브러리는 추가하지 않고 F-01에서 실제 확인·고정한 도구를 재사용합니다.
전체 예정 명령: `JAVA_HOME=$(/usr/libexec/java_home -v 21) ./gradlew spotlessCheck check bootJar`와 `./scripts/verify.sh`입니다. 스크립트도 JVM 21을 지정합니다. Java 타입 검사는 main/test 컴파일로 확인합니다.
F-01의 공통 명령은 구축됐습니다. 기능별 예정 검사는 실제 실행 증거와 구분합니다. 로그·대상 코드·실행 환경·종료 코드·테스트 수·AC별 결과는 [verification.md](verification.md)에 기록합니다. UI가 없어 브라우저 검사는 적용하지 않습니다.
각 커밋은 논리 단위 300~400줄 이내이며 초과 시 테스트 시나리오/하네스 책임별로 나눕니다. 관련 변경만 스테이징하고 push·배포·무관한 리팩터링은 하지 않습니다.
자체 검사 후 `fork_turns="none"`의 새 컨텍스트 읽기 전용 리뷰어에게 승인 계약·설계·기준 커밋·새 파일 포함 diff·코드·실행 증거를 전달합니다. 발견 사항 수정 후 재검증하고 정확성 변경은 재리뷰합니다.
[review.md](review.md)에 리뷰 대상·세션·지적·수정·재검토를 기록합니다. 2패널 동료 계획 검수는 이 제품 독립 리뷰를 대신하지 않습니다.
관련 하위 단위도 검사·독립 검토 후 커밋하고 기능 전체 필수 검증·리뷰·차단 해소·커밋 일치 확인을 마친 뒤 다음 기능으로 이동합니다.

## 실제 실행 대조
F-02 완료 기준 60078e1, 선행 JUnit16건·전체verify 통과입니다. AC-01의 8×256 고정 시각 검사는 기존 SnowflakeGeneratorTest를 재사용합니다. 신규 SnowflakeConcurrencyTest는4097회, IdConcurrencyIntegrationTest는실제 HTTP2048회입니다. 테스트 전용 ConcurrentCalls/ConcurrentCallsTest로 공통 deadline·모든 결과 회수·실패/timeout 정리를 검사합니다. 하네스 신규 동작은 RED3건을 확인한 뒤 구현했고, 기존 생성기는 수정하지 않았습니다. 실제 서버 테스트는 Spring 컨텍스트 준비 뒤 순차2건을 별도 기록하고 동시2048건과 분리합니다.

HTTP 준비는 SpringBootTest RANDOM_PORT 컨텍스트가 실제 서버 시작을 완료한 뒤 첫 실제 POST를 5초 한도로 검사합니다. 재시도로 성공을 숨기지 않고 30초보다 짧은 한도에 검증합니다. 새 하네스는 ready latch로 8개 작업자 준비 후 main이 시작 장벽을 해제하며, 기존2048 core 검사도 단일deadline으로 정합화합니다.
