# 이슈 실행 규칙

## 요청과 기록의 기준
이슈 하나는 사용자 행동 하나의 성공·실패 경로를 끝까지 구현하는 단위다.
[이슈 템플릿](../templates/issue.md)은 요청, [기능 계획](../features/template.md)은 실행 방법을 담는다.
GitHub 이슈가 있으면 요구사항의 기준으로 삼고 plan.md에 URL·번호·확인 날짜를 기록한다.
이슈가 없으면 제공받은 요청을 계획에 기록한다. 번호나 URL을 만들어내지 않는다.
원격 이슈 생성·편집·종료와 메시지 전송은 별도 요청 범위에서만 수행한다.

## 조사와 계획 승인
저장소 지침, 기존 코드, 변경 상태, 관련 설계와 이슈 내용을 먼저 읽는다.
AC-01 같은 완료 조건 ID를 유지하고 조건별 테스트와 실제 동작 확인 방법을 연결한다.
변경 파일, API·DB·설정·인증 영향, 호환성, 제외 범위를 제시한다.
새 의존성은 필요성·기존 도구를 쓰는 대안·유지 비용을 설명한다.
관련 없는 리팩터링을 포함하지 않는다.
기능 계획 승인 후 구현한다. 이미 승인한 범위의 수정·재검증은 다시 승인받지 않는다.
요구사항이나 계약이 바뀌면 변경 이유와 승인 내용을 계획에 남긴다.
구현 도중 이슈가 바뀌면 승인 계획과 차이를 확인하고 충돌을 해결한 뒤 계속한다.

## 구현과 검증
메인 에이전트 하나가 필요한 계층을 연결한다. 없는 UI·DB·인증을 임의로 추가하지 않는다.
사용자별 데이터가 있다면 인증 정보의 출처와 서버의 접근 제어를 계획·테스트에 명시한다.
관련 테스트·타입 검사·빌드를 실제 실행한다. Java 타입 검사는 컴파일로 확인한다.
UI는 브라우저에서 정상·입력 오류·서버 또는 네트워크 실패 상태를 확인한다.
필수 검증을 실행하지 못하면 이유와 영향을 기록하고 검증 보류로 둔다.
해당 기능에 없는 계층은 적용하지 않음으로 표시한다. 미실행과 혼동하지 않는다.

## 독립 리뷰와 수정
새 컨텍스트 리뷰어에게 [리뷰 템플릿](../templates/review.md)의 자료를 제공한다.
기준 커밋부터의 변경뿐 아니라 새 파일·미커밋 변경도 포함한다.
리뷰어는 코드를 직접 읽고 판정한다. 구현자의 성공 설명만으로 통과시키지 않는다.
메인 에이전트가 수정하고 관련 검증을 재실행하며 정확성 변경은 재리뷰한다.
필수 검증·독립 리뷰 통과와 차단 결함 해소 후 검증한 변경만 작은 커밋으로 남긴다.
