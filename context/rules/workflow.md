# 기능별 워크플로우

한 작업은 사용자 행동 하나를 끝까지 처리한다.
[실습 스킬](../skills/snowflake-practice/SKILL.md)과 [기능 목록](../tasks.md)을 읽는다.

## 1. 계획
이슈 요청은 [이슈 실행 규칙](issue-execution.md)과 [기능 계획 템플릿](../features/template.md)을 따른다.
메인 에이전트가 기존 코드·변경 상태·요구사항을 확인한다.
변경 파일, API·DB·설정 영향, 정상·실패 조건, 검증 방법을 기능 plan.md에 제시한다.
사용자가 기능 계획을 승인하면 구현한다. 승인한 범위의 수정을 다시 묻지 않는다.

## 2. 구현
메인 에이전트 하나가 필요한 계층을 연결한다. 작은 기능을 계층별 에이전트로 나누지 않는다.
변경 범위를 보존하고 계약 변경이 필요하면 계획과 결정 기록을 갱신해 확인받는다.

## 3. 자체 검증
관련 테스트·타입 검사·빌드·실행 검사를 실제 수행한다.
UI 작업이면 브라우저 정상·실패 상태를 확인한다.
실행 버전·명령·결과·미실행 항목을 기능 verification.md에 남긴다.

## 4. 독립 리뷰
전체 구현 대화 없이 새 컨텍스트의 리뷰어를 시작한다.
승인 요구사항·설계·기준 커밋·새 파일을 포함한 diff·코드·테스트·실행 증거를 제공한다.
리뷰어는 읽기 전용으로 검토하고 기능 review.md에 판정과 근거를 남긴다.

## 5. 수정·재검증·커밋
메인 에이전트가 결함을 수정하고 관련 검사를 재실행한다.
정확성에 영향을 주는 수정은 재리뷰한다.
필수 검증·독립 리뷰 통과와 차단 결함 해소 후 검증한 코드를 커밋한다.
태그는 feat/fix/refactor/design/comment/chore/docs/hotfix, 설명은 한국어로 쓴다.
논리 단위당 약 300~400줄 이내로 나누고 관련 파일만 스테이징한다. push는 사용자가 한다.
큰 기능의 하위 커밋도 검토·검증하며 기능 전체가 끝나기 전에 다음 기능 구현을 시작하지 않는다.
필수 검사나 리뷰를 못 하면 검증 보류다. 완료 보고만으로 다음 단계로 넘기지 않는다.
tasks·progress를 갱신하고 다음 기능의 계획으로 이동한다.
